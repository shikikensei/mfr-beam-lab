# モデルの仮定（5章「前提と文献」の元原稿）

フェーズ1時点。論文は Smouse, Liu & Sylvester (2020) を指す。
「論文にない」と書いた項目は、このツールが説明のために置いた仮定である。

## 0. 方式の呼び名と、論文との関係

| 画面上の名前 | 中身 |
|---|---|
| 動的RSI＋先読み（本ツールの拡張） | 既定。論文の記述どおりの手順に、「待っている後続の固定タスクが許容範囲を失わないよう、NFTの仮置きを前へずらす」処理を足したもの。**論文にない**。論文は「先読みなし」と明記している |
| 動的RSI（論文の記述どおり） | 論文の文章と図から読み取れる手順を、本ツールが解釈して実装したもの。論文が決めていない点は2節のとおりに埋めている |
| 従来型（固定長の箱） | 4節の定義 |

- 既定の方式を「論文の方式」とは呼ばない。
- 「論文の記述どおり」の成績は、**本ツールの解釈と説明用シナリオでの結果** であり、論文の方式そのものの優劣を示さない。
- 論文には、シミュレーションの条件（キューの構成、負荷の内訳、DRSIの最大長の値、負荷の水準）も、結果の数値や表も **載っていない**。載っているのは、手順の説明、FTDの計算例1つ、図3〜7、次の定性的な記述だけである。
  - 長い時間で平均すれば所望フレームタイムはおおむね満たされる
  - 固定タスクの取りこぼしは少ない。例外は、要求時刻のせいで上位の固定タスクが実行できなくなる場合
  - 1つのタスクが優先度だけでタイムラインを占有しない。過負荷ではなだらかに劣化する
  - 性能はスラックやDFTなどの入力に左右される
- したがって、論文の数値との照合はできない。図の構成（固定2キュー、柔軟4キュー）に寄せ、数値は本ツールが置いたシナリオで、上の定性的な記述と比べた結果は `scripts/paper-check.ts` にある。

## 1. 固定キューの優先順位

高い順に、**緊急 ＞ 確認 ＞ 再照射 ＞ 高機動追尾 ＞ 追尾**。

| キュー | 理由 |
|---|---|
| 緊急 | 論文の「緊急の固定タスク」。優先度が高く、要求時刻が近く、スラックがない |
| 確認 | 探知直後で、まだ航跡がない。逃すと捜索で見つけ直すまで情報が何もなくなる。Han (2024) の表でも確認が追尾より上 |
| 再照射 | 既存の航跡が1回外した直後。通常の更新が遅れても精度が落ちるだけだが、再照射を逃すとロストに近づく。確認より下なのは、航跡の予測がまだ残っているため |
| 高機動追尾 | 予測誤差の増え方が速く、更新間隔が短い。Han の表の「精密追尾 ＞ 通常追尾」に対応 |
| 追尾 | 上記以外の定期更新 |

確認・精密追尾・通常追尾の順は Han の表1に合わせた。再照射の位置は **論文にない**。

## 2. 動的RSI：論文が決めていない点の埋め方

| 項目 | このツールの扱い |
|---|---|
| NFTの候補 | 各キューの先頭1件（論文どおり）。先頭は最遅開始時刻が最も早い要求 |
| 3つ以上のキュー | 候補のうち期限（最遅開始）が最も早いものを調べる。より上位の候補の前に収まれば選ぶ（ケース1・2）。収まらなければ外して次を調べる |
| ケース2の仮置き位置 | 自分の最遅位置と「上位の候補の最遅開始 − 自分の長さ」の早い方。上位が必ず後に続けられる |
| ケース3の「返す」 | 上位の前にも後ろにも入らない要求を返す。返された要求は待ち行列に残り、許容範囲を過ぎた時点で取りこぼしになる |
| 不足量（FTD） | 箱を決めた時点で1回だけ計算。不足の大きい領域から、不足を解消する本数（切り上げ）か、入るだけ詰める |
| パターン開始時刻 | 前のフレームが終わった時刻。フレームタイムは完了から完了までで測る |
| 箱の最大長 | 「最遅位置で置くと箱が最大長を超える」固定タスクは候補にしない。候補がなければ捜索だけで箱を閉じる。その箱は、待っている固定タスクの最遅開始を越えない |
| 固定タスクの連結 | NFTの直後に、許容範囲がその時刻を含む要求を期限の早い順に続ける。箱が最大長を超える手前で止める |
| 割り込み | 緊急タスクはシナリオに書いたイベント。要求時刻の少し前に通知される。通知時点で始まっていないものはキューへ戻し、実行中のドウェルは完了させ、緊急タスクをNFTにして箱を組み直す。通知は最長ドウェルより前でなければならない |
| 取りこぼしの影響 | 追尾更新・再照射の取りこぼしは「外れ」1回と同じ扱い。確認の取りこぼしは未探知に戻る |

## 3. 余った時間の扱い（論文との違い）

- **所望ペースまで（既定）：** 論文の「不足量がゼロになるまで」をそのまま採る。捜索が足りているときの空きは「余裕」と呼び、隙間には数えない。この場合、固定タスクは仮置き位置から要求時刻まで寄せて実行する（論文は「隙間が閉じるまで寄せる」としか書いていない）。
- **埋め切る：** 不足量にかかわらず空きを捜索で埋める。残った空きはすべて隙間。
- **隙間** は「入れたかったが入らなかった時間」。スケジューラ効率は論文どおり（全時間 − 隙間）÷ 全時間。

## 4. 従来型の定義

論文の記述は「固定長のRSIを、優先度の高いキューから順に埋める」まで。それ以外は次のように置いた。**従来型が不当に不利にならない** ことを基準にしている。

- 箱は固定長（既定 100 ms）で、時刻0から等間隔。
- 固定タスクは優先度順に、要求時刻に置く。ふさがっていればスラック内で最も近い空きに置く。
- 箱の境界をまたぐ配置はしない。入らなければ次の箱へ持ち越し、持ち越しても間に合わなければ取りこぼし。
- 捜索は優先度順。各領域が求める本数は動的RSIと同じ計算（箱の先頭での不足量）。違いは順番と、寄せて隙間を閉じないことだけ。
- 緊急タスクの通知による打ち切りは動的RSIと同じ。

## 5. 説明用シナリオの数値

特定の装置の値ではない。少数目標・長めのドウェルにして、1手ずつ追えるようにしたもの。

- 捜索：水平線 12ビーム × 15 ms（所望 0.6 s）、上空 20ビーム × 10 ms（所望 1.0 s）
- 追尾：高機動は 0.3 s ごと、その他は 0.6 s ごと。スラックは前後とも更新間隔の 8 %。ドウェル 8〜16 ms
- 確認：探知の 100 ms 後を要求、前 90 ms・後 100 ms、長さ 12 ms
- 再照射：外れの 30 ms 後を要求、前 25 ms・後 60 ms
- 探知確率：捜索 0.85、確認 0.92、追尾 0.88。3回続けて外すとロスト
- 命中判定の乱数は「目標と、その目標への何回目の照射か」で決まる。並べ方が違っても同じ照射は同じ結果になる
- ドウェルは送信・待ち・受信の3区間で持つ。フェーズ1では待ち0

## 6. 取りこぼしのテストで使う定義

論文は「取りこぼしは少ない」としか書いていない。次の2つは本ツールが置いた値である。

- **飽和していない負荷：** 公称需要が全時間の 90 % 以下。公称需要 ＝ 全捜索領域を所望フレームタイムで回す時間 ＋ 全目標を更新間隔どおりに追尾する時間。確認照射と再照射は含めない（スケジューラの結果で変わるため）。説明用シナリオでは再照射が追尾の約 12 %（＝ 1 − 追尾の探知確率）加わり、この付近の負荷で約 5 ポイントになる。残りの余白は、ドウェルを分割できないことによる端数のため。
- **一定割合：** 30秒の実行で、固定タスクの要求の 3 % 以下。取りこぼした更新は「外れ1回」と同じ扱いで、このシナリオではレーダ自体が 12 % 外す。スケジューラ起因の外れをその4分の1までに抑える、という基準。実測の最悪値（8種）は、論文の記述どおりで 1.7 %、＋先読みで 0.0 %（`scripts/droprate.ts`）。

## 7. 取りこぼしの件数が何に依存するか（5章に書くこと）

- 取りこぼしの件数は、本ツールが足した「外れと再照射・確認」のモデル、スラックの幅、箱の最大長に強く依存する。**論文にこれらの値はない。**
- 図の構成（固定2キュー、柔軟4キュー）に寄せたシナリオで、論文の記述どおりの実装（`scripts/paper-check.ts`、60秒 × 8種の平均）：
  - 外れなし：取りこぼしは合計需要 96 % で 0.4 %、119 % で 1.1 %
  - 外れあり（説明用シナリオと同じ探知確率）：同じ負荷で 2.7 %、8.4 %
  - スラックを ±32 % にすると 96 % でほぼ 0 件。箱の最大長 75／150／300 ms で 14.9／8.4／3.5 件
- したがって、件数の大小を論文の方式そのものの優劣として書かない。設定を変えても残る違いは、隙間と、捜索に回せる時間である。

## 8. 「待っている上位の固定タスクが、後から置かれた下位に場所を取られて落ちる」件数

`scripts/droprate.ts` の出力（説明用シナリオ、30秒 × 8種の合計。分母は取りこぼしの総数）。

| 目標数（公称需要） | 論文の記述どおり | ＋先読み |
|---|---|---|
| 2〜12（53〜88 %） | 0 | 0 |
| 14（81〜92 %） | 1 / 94 | 0 / 0 |
| 16（88〜98 %） | 6 / 190 | 0 / 10 |
| 18（93〜104 %） | 5 / 343 | 2 / 37 |
| 20（99〜109 %） | 26 / 607 | 7 / 95 |
| 24（106〜124 %） | 92 / 1272 | 12 / 269 |
| 30（126〜142 %） | 348 / 2539 | 26 / 720 |
| 40（150〜169 %） | 1122 / 5057 | 66 / 2162 |

- **論文の記述どおり：** この性質はテストしない。1回通し・先読みなしの方式が約束していない性質だからである。原因は、候補が各キューの先頭だけであること、上位を守る確認が1手先までであること。箱の中で上位候補を守ること（ケース2・3）は単体テストで確認している。
- **＋先読み：** 飽和していない負荷（公称需要 90 % 以下）で 0 件であることをテストしている。
  - 連結のとき、キューの先頭だけでなく待っている要求すべてを見る。下位を続ける前に「いま間に合う上位の要求が、その後も全部間に合うか」を期限順に確かめる。この変更で、目標24の件数は 22 → 12、目標40は 414 → 66 になった。
  - **限界：** 過負荷で残る分は、箱を実行している間に新しく届いた上位の要求（主に再照射）による。計画した時点では存在しない要求なので、届くことを見込んで余白を残さない限り防げない。本ツールはそこまでは行わない。

## 10. 2・3章の5つの並べ方（到着順、固定テンプレート、固定優先度、最早期限優先、タイムバランス）

特定の文献の手順ではない。名前の示す規則を、本ツールが1章と同じ世界（同じ要求・許容範囲・乱数）の上に単純な形で書いたもの（`src/engine/simple.ts`）。

| 項目 | 扱い |
|---|---|
| 単位 | 1回の呼び出しでドウェルを1つ選ぶ |
| 固定タスクの「用意ができた」 | 要求時刻。要求時刻より前には実行しない（前側のスラックは使わない）。最遅開始を過ぎれば取りこぼし |
| 捜索ビームの「用意ができた」 | 所望のペースで回したとき、そのビームを終えているべき時刻（ビーム終了時点のFTD ≥ 0）。一巡がちょうど所望フレームタイムになる。「埋め切る」設定では常に用意ができている |
| 遅れている捜索ビーム | **既定は「遅れを覚えない」**：遅れているビームは「いま用意ができた」ものとして扱う。動的RSIの不足量もパターン一巡ごとに数え直すので、扱いが揃う。3章で「覚えておく」に切り替えられる。5方式で共通の取り決めで、方式ごとに有利な組み合わせは選ばない（11節） |
| 期限 | 固定タスクは最遅開始 ＋ 長さ。捜索ビームは用意ができた時刻 ＋ 1ビームぶんの持ち時間（DFT × ビーム長 ÷ パターン長） |
| 到着順 | 用意ができた時刻の早い順 |
| 固定優先度 | 固定キューの順、そのあと捜索領域の優先度順 |
| 最早期限優先 | 期限の早い順 |
| タイムバランス | （現在 − 用意ができた時刻）÷ 周期 の大きい順。周期は、追尾は更新間隔、確認は確認までの待ち時間、再照射は再照射までの待ち時間、捜索は1ビームぶんの持ち時間。**この取り方で結果は変わる** |
| 固定テンプレート | 100 ms 周期。先頭 40 % が固定タスク用、残りが捜索用。枠内は期限順。ドウェルは枠内で終わらなければ置かない。相手が欲しがっていた空きは隙間に数える |
| 緊急タスク | 通知後は、その開始時刻をまたぐドウェルを始めない。緊急タスクはどの枠でも実行する |

- **上位タスクの取りこぼし：** 通常の追尾更新より上の4キュー（緊急・確認・再照射・高機動追尾）の取りこぼし件数。
- 4つの状況 × 8方式の数値は `scripts/methods.ts`、キュー別の取りこぼしは `scripts/upper.ts` の出力。

## 11. 到着順・最早期限優先・タイムバランスの成績は、取り決めにどれだけ左右されるか

`scripts/conventions.ts` の出力（飽和する状況：目標30が40秒で現れる60秒間、4種の平均）。捜索は「頼みたい量のうち実行できた割合」、取りこぼしは件数（要求に対する割合）。

| 方式と取り決め | 捜索 | 取りこぼし |
|---|---|---|
| 固定優先度 | 69 % | 148（4.9 %） |
| 従来型 | 56 % | 207（6.7 %） |
| 動的RSI（論文の記述どおり） | 72 % | 290（9.3 %） |
| 動的RSI＋先読み | 68 % | 67（2.3 %） |
| 到着順：遅れを覚えておく | 96 % | 1531（41.0 %） |
| 到着順：遅れを覚えない（**既定**） | 71 % | 97（3.3 %） |
| 最早期限優先：遅れを覚えておく（捜索の期限は1ビームぶん後） | 97 % | 855（27.7 %） |
| 最早期限優先：遅れを覚えない（**既定**） | 71 % | 60（2.1 %） |
| 最早期限優先：遅れを覚えておき、期限を 0.3／2／4／12 ビームぶん後 | 99／93／88／76 % | 1006／754／585／286 |
| 最早期限優先：期限4ビームぶん後、遅れは1ビームぶんまで覚える | 68 % | 29（1.0 %） |
| タイムバランス：遅れを覚えておく（周期で割る） | 95 % | 1633（42.4 %） |
| タイムバランス：許容範囲の幅で割る | 96 % | 1039（32.1 %） |
| タイムバランス：遅れを覚えない（**既定**） | 70 % | 105（3.5 %） |

- **設定で変わる差：** 3方式の取りこぼし件数。取り決め次第で 29 件から 1600 件まで動く。「遅れを覚えておく」ときの「動的RSI系より桁違いに悪い」成績は、取り決めの結果であり、規則の良し悪しではない。
- **なぜそうなるか：** このモデルでは、固定タスクには許容範囲があって過ぎれば落ちるが、捜索には「落ちる」がない。捜索と固定タスクを同じ物差しで並べる規則では、あふれた分をすべて固定タスクがかぶる。捜索を後回しにできる取り決めにすると、あふれた分は捜索がかぶり、成績は固定優先度に近づく。
- **設定を変えても残る差：**
  - どの取り決めでも「捜索 約95 %・取りこぼし 約4割」か「捜索 約70 %・取りこぼし 数%」のどちらかの側に寄り、両方を取れる取り決めはない（需要が上限を超えているため）。
  - 隙間はどの取り決めでも 0 %。隙間が出るのは従来型（7.5 %）と固定テンプレートだけ。
  - 捜索を削る側に寄せたとき、3方式は領域ごとの偏りが大きい（水平線 78〜84 %、上空 50〜54 %）。動的RSIは 68／69 % と均等に削る。
- **採った取り決め：** 既定は「遅れを覚えない」。「期限4ビームぶん＋遅れ1ビームぶん」のような、特定の方式に有利な調整は採らない。タイムバランスは周期で割る。

## 12. 固定テンプレートの成績は、枠の配分にどれだけ左右されるか

`scripts/template.ts` の出力（60秒、4種の平均）。配分は「周期のうち固定タスク用の割合」。

| 配分 | 飽和：捜索 | 飽和：隙間 | 飽和：取りこぼし | 軽い：隙間 | 軽い：取りこぼし |
|---|---|---|---|---|---|
| 20 % | 100 % | 28.1 % | 1682（66.0 %） | 17.8 % | 397（37.2 %） |
| 30 % | 100 % | 21.3 % | 1339（53.0 %） | 13.5 % | 145（14.0 %） |
| 40 %（既定） | 100 % | 12.2 % | 1294（44.1 %） | 9.7 % | 52（5.1 %） |

- **設定で変わる差：** 取りこぼしと捜索の実行率。配分を動かすと、どちらを守るかがそのまま入れ替わる。

## 14. 2勾配ベネフィット関数の並べ方（`src/engine/tsbf.ts`）

**原文未確認の要約に基づく実装。** 元は P. W. Moo, DRDC Ottawa TM 2010-259 (2010) の二次要約（リポジトリには含めていない）。同じ手法が査読論文（IET RSN 5(8), 884–894, 2011）と書籍（Moo & Ding, 2015, 4.2節）にあるが、どちらも未入手。査読論文の要旨では「優先度の高い捜索を追尾と一緒に先に並べる」形で、報告書の要約と少し違う。本ツールは **報告書の要約の版**（追尾を先、捜索はすべて後から埋める）に基づく。原文が入ったら、版の違いも含めて照合する。

| 項目 | 扱い | 出どころ |
|---|---|---|
| 全体の流れ | 窓ごとに、追尾を選んで開始時刻を決め、残りを捜索で埋める | 要約 |
| 過負荷時の選別 | ピークの高い順に1つずつ加え、成立しなくなるものを落とす。成立判定は希望時刻順の「条件付き最早開始」 | 要約 |
| 開始時刻 | ベネフィットの合計を最大化。順序の入れ替えなし | 要約 |
| 解き方 | 動的計画法（報告書は単体法）。候補を各照射の最早・最遅・希望時刻に絞れることを使う。総当たりと一致することをテスト | **本ツール** |
| ピーク | 緊急 1000、確認 400、再照射 300、高機動 200、追尾 100 | **本ツールが置いた値** |
| 傾き | 前後とも同じ、全照射共通（要約の例題も δ = Δ） | **本ツールが置いた値** |
| 窓の長さ | 既定 100 ms。3章で 300 ms（報告書の例題の公称値）に切り替え可 | **本ツール** |
| 窓に入れる要求 | 要求時刻が窓の終わりより前のもの | **本ツール** |
| 窓の境界 | またがない。入らない要求は、許容範囲が次の窓に届けば持ち越し、届かなければ取りこぼし | **本ツールの追加**（報告書にない） |
| 捜索の埋め方 | 領域ごとに保留1本。しきい時間 ω ＝ DFT ÷ ビーム数。経過時間 ≥ ω を前へ（ω の小さい順、次に経過時間の長い順）、残りは経過時間の長い順。1本より短い隙間は残す。経過時間は前回の照射の開始から測る | 要約 |

- 「待つうちに期限切れ」は全件、窓の途中で届き、次の窓が始まる前に許容範囲が切れた要求（再照射が大半、300 ms では確認照射も）。再照射は外れの 30 ms 後を要求し、後ろのスラックは 60 ms なので、窓が約 90 ms より長いと間に合わないものが出る。
- これは「窓の先頭で要求がそろっている」前提の方式を、要求が途中で生まれる本ツールのモデルに当てはめた結果である。方式そのものの優劣としては書かない。
- 上の表は「埋め切る」設定での値。捜索が 100 % を超えるのは、入るだけ詰めるため。
- 「所望ペースまで」（2・3章の既定）では、窓 100 ms で、軽い：捜索 100 %・余裕 29.2 %・取りこぼし 11（1.1 %）、飽和：捜索 58 %・余裕 8.4 %・取りこぼし 83（2.8 %）。窓 300 ms で、軽い：捜索 99 %・取りこぼし 137（14.0 %）、飽和：捜索 76 %・余裕 11.8 %・取りこぼし 491（16.2 %）。飽和の「余裕」は、目標が出そろう前の、まだ時間が足りている区間のもの。
- 経緯：最初は「経過時間がしきい時間 ω に達した領域だけを候補にする」としていた。これだと遅れを取り戻せず、捜索が遅れているのに時間が余り（飽和で捜索 46 %・余裕 14.5 %）、ほかの方式の「所望ペースまで」と意味が違っていたため、上の形に直した。
- 「軽負荷で取りこぼしゼロ」のテストは、窓 100 ms には適用し（目標2で通る）、300 ms には適用しない。

### 2勾配ベネフィットのスローモーション（1章）

- 4手：窓の要求を集める → 選別する → 開始時刻を一括で決める → 隙間を捜索で埋める。
- 山の図は **模式図**。高さは本ツールが置いたピーク（優先順位）に比例、傾きは全照射で共通。実際の計算では、傾きが共通なので、開始時刻の決定にピークは効かない（ピークが効くのは選別だけ）。
