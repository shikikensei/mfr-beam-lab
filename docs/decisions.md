# 作者に聞かずに決めたこと

作者が席を外している間（2026-11-21〜）に、指示の基準に沿って決めたことの記録。
1件ごとに、何を決めたか、ほかの案、選んだ理由、あとで変えるときに触る場所。

## フェーズ4（パルスインターリーブ）

### D4-1 1つの待ちに差し込む照射は1つまで
- **ほかの案：** 待ちに入るだけ詰める／差し込まれた照射の待ちに、さらに次を入れる（連鎖）。
- **理由：** Han は「差し込む相手は直前の照射1つ」としている。入るだけ詰めると効果が大きく出て、待ちの長さという本ツールの置いた値への依存が強まる。控えめな側を選んだ。
- **変えるとき：** `src/engine/simple.ts` の `planInterleave`（`break` で1つ目で止めている）。検証は `metrics.ts` の `validate`。

### D4-2 差し込む照射は「いまの照射を始める時点で用意ができているもの」から、優先度の高い順に最初に入るもの
- **ほかの案：** 待ちの間に用意ができるものも候補にする／浮く時間が最大のものを選ぶ。
- **理由：** 土台の固定優先度と同じ物差し（優先度）で選ぶほうが、差が差し込みだけの効果として読める。浮く時間で選ぶと、優先度の低い照射が先に実行されることがある。
- **変えるとき：** 同じ `planInterleave` の候補の並べ方。

### D4-3 遠距離かどうかは目標の番号で決める（乱数を引かない）
- **ほかの案：** 乱数で決める。
- **理由：** 乱数を1回余分に引くと、ほかの方式の結果（目標の位置や機動の割り当て）が全部変わる。「属性を足す前と変わらない」をテストで保証するため。
- **変えるとき：** `src/engine/scenario.ts` の `makeScenario`（`far:` の行）。

### D4-4 待ちを持つのは追尾更新と再照射だけ。確認照射には待ちを持たせない
- **ほかの案：** 遠距離の目標の確認照射にも待ちを持たせる。
- **理由：** 確認照射は長さが一定（12 ms）で、探知直後の1回だけ。持たせても効果は小さく、説明が増える。作者の指示は「遠距離は送信 2 ms ＋ 待ち ＋ 受信 2 ms」「捜索は待ちなし」で、確認照射には触れていないので、足さない側にした。
- **変えるとき：** `src/engine/simulate.ts` の `addRequest`（`far` の条件）。

### D4-5 送信デューティ比の数え方
- **決めたこと：** 待ちのある照射は送信区間（2 ms）、それ以外は長さの半分を送信と数える。
- **ほかの案：** すべての照射で長さ全体を送信と数える。
- **理由：** エンジンは最初から、待ちのない照射を「前半が送信、後半が受信」として持っている。それに合わせた。この数え方だと、遠距離の割合を上げるとデューティ比そのものは下がる（送信 2 ms の照射が増えるため）。比べるのは、同じ状況での固定優先度とインターリーブ。
- **変えるとき：** `src/engine/metrics.ts` の `summarize`（`tx +=` の2か所）。

### D4-6 スローモーションの既定の場面では差し込みがほとんど起きないので、⑤に「差し込み」の場面を2つ足した
- **ほかの案：** インターリーブを選んだら目標数を自動で増やす。
- **理由：** 目標6の説明用シナリオでは、照射が立て込まず、差し込む相手がいない。設定を勝手に変えるより、起きる場面（目標16）へ飛ぶボタンのほうが、ほかの場面と同じ操作で済む。
- **変えるとき：** `src/main.ts` の `SCENES`。

### D4-7 2・3章の柱は、インターリーブでは 100 % を超えて積み上がる
- **ほかの案：** 100 % で切る／共有した時間を別の色で描く。
- **理由：** 「同じ時間に2つの照射が入る」ことが、柱が上限の線を越えることでそのまま見える。色を増やさずに済む。
- **変えるとき：** `src/ui/charts.ts` の `stackChart`。

## フェーズ5（配る層、4章）

### D5-1 品質・効用の式と重みの形
- **決めたこと：** 追尾の品質 ＝（1 − e^(−ドウェル長/6 ms)）÷（1 ＋（更新間隔/τ）²）、τ は高機動 0.35 s・通常 0.8 s。捜索の品質 ＝ 1 ÷（1 ＋ 0.5（一巡/元のDFT）²）。重みは高機動 1.4、通常 1、水平線 6、上空 4。
- **ほかの案：** 1章の「外れ」のモデル（探知確率）とつなげる。
- **理由：** 指示は「説明用の自作、自作と明記」。エンジンの探知確率は設定によらず一定なので、つなげると新しい物理モデルを足すことになる。足さない側を選んだ。捜索の重みは、領域1つが目標数個ぶんに見合うように置いただけ。
- **変えるとき：** `src/engine/qram.ts` の `trackQuality`、`searchQuality`、`WEIGHT`。式は画面（5章）にも書いてあるので、そこも直す。

### D5-2 選べる設定の一覧
- **決めたこと：** 更新間隔5通り × ドウェル3通り、所望フレームタイム5通り。
- **理由：** 曲線が1枚の図で読める数。いまの既定値（0.3／0.6 s、8〜16 ms、元のDFT）を含む。
- **変えるとき：** `qram.ts` の `Q_INTERVALS`、`Q_DWELLS`、`Q_DFT_FACTORS`。

### D5-3 格上げは「収まらなくなったら止める」。飛ばして続けない
- **ほかの案：** 収まらない格上げを飛ばして、収まるものを探し続ける（使い残しが減る）。
- **理由：** 作者の指示が「上限で止める」。読めた2本の説明もこの形。改良すると「Q-RAM の骨格」と言えなくなる。最適でないことは測って書いた。
- **変えるとき：** `qram.ts` の `allocate` の `break`。

### D5-4 配分は「目標が全部そろった状態」で1回だけ決める
- **ほかの案：** 目標が現れるたびに配り直す。
- **理由：** 層の違いを見せるのが目的。配り直しを入れると、時間とともに設定が変わり、2章の「入れたい量」の線の意味が変わる。控えめな側を選んだ。目標が出そろう前は、上限より少なく頼むことになる。
- **変えるとき：** `qram.ts` の `applyAllocation`（シナリオ全体に1回適用）と、`src/ui/lab.ts` の `build`。

### D5-5 配分は乱数の種ごとに計算し直す
- **理由：** 3章の成績は4種の平均。どの目標が高機動かは種で変わるので、種11の配分を別の種に当てると食い違う。同じ上限で種ごとに配る。
- **変えるとき：** `src/ui/lab.ts` の `build`。

### D5-6 2・3章に配分が入っている間は、上に帯で知らせ、「元の状況に戻す」を置く
- **理由：** 配分を入れたまま3章を見ると、成績が既定と違う理由が分からなくなる。
- **変えるとき：** `src/ui/lab.ts` の `allocBanner`。

### D5-7 曲線は仕事の種類ごとに1枚（水平線、上空、高機動の目標、通常の目標）
- **ほかの案：** 目標ごとに1枚（30枚）。
- **理由：** 同じ種類の目標は同じ曲線。1枚にまとめ、選ばれた点にその設定になった目標の数を書くほうが読める。

## フェーズ6（仕上げ）

### D6-1 URLの形と、入れる設定
- **決めたこと：** `#ch3?p=sat&m=plus&a=priority&b=plus&s=11` の形（章の番号のあとに設定）。入れるのは、状況 p、2章の並べ方 m、3章のA・B、乱数の種 s。既定と違うときだけ、遅れの扱い k、2勾配の窓 w、4章の配分の上限 q、見ている1秒 t。1章の設定（目標数、手順の位置）は入れない。
- **ほかの案：** `?` で始まる通常のクエリにする／1章の状態も入れる。
- **理由：** これまで章の移動に `#ch番号` を使っており、同じ場所に足すのがいちばん変更が小さい。指示は「状況、並べ方、乱数の種」。1章は手順の位置まで入れると長くなるので足さなかった。読めない値は無視して、いまの設定のままにする。
- **変えるとき：** `src/ui/lab.ts` の `labQuery`／`applyLabQuery`、`src/main.ts` の `syncAddress`／`readAddress`。
- **注意：** クロード側のプレビューは `#名前` だけの形しか受け付けないので、URLの書き換えは失敗しても黙って続ける。共有の確認は公開ページか手元（`npm run dev`）で行う。
